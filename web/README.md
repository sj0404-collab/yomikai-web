# ownocr-web — распознавание манги в браузере, по-настоящему

Замена присланной страницы «NeuroManga OCR WebWASM»: тот файл показывал вписанные
руками строки и ждал 0,6 с, чтобы это выглядело как работа нейросети. Здесь всё
считается на месте — те же модели, что в приложении, через `onnxruntime-web` (WASM),
без обращений к серверу.

```
страница → детектор строк (koma_det.onnx)       → карта вероятностей текста
         → компоненты связности + расширение    → боксы облачков
         → резка бокса по проекции чернил       → рамки строк
         → дочистка рамок (weak + дубли)        → 41 рамка вместо 50
         → чтец строк (koma_rec.onnx, CTC)      → текст
         → чистка текста (крякозябры, цифры)    → слова
         → порядок чтения манги (справа налево сверху вниз)
```

## Как запустить

**Вариант 1 — папка (модели грузятся по сети, первый экран сразу):**

```bash
python3 web/serve.py 8099      # http://localhost:8099/
```

Свой сервер, а не `python3 -m http.server`: для `.wasm` нужен тип `application/wasm`,
иначе часть браузеров не даёт собрать модуль потоково.

**Вариант 2 — один файл (32 МБ, работает даже с `file://`, без сети и сервера):**

```bash
python3 web/build_single.py    # → web/ownocr-web-single.html
```

Модели, wasm, словарь и три примера страниц зашиты в base64 — открывается двойным
щелчком. Этот файл в git не лежит (32 МБ), он собирается скриптом.

## Что внутри

| файл | что делает |
|---|---|
| `core.js` | весь движок: детектор, резка на строки, дочистка рамок, чтец CTC, чистка текста, порядок чтения. Без DOM — поэтому гоняется и в Node |
| `index.html` | интерфейс: страница, оверлей рамок, список реплик, честная статистика по шагам |
| `serve.py` | сервер с правильными типами и без кэша |
| `build_single.py` | сборка одного html |
| `data/` | три эталонные страницы + словарь 25 000 слов |
| `vendor/` | `ort.min.js` 1.19.2 и `ort-wasm-simd-threaded.wasm` (11 МБ) |
| `test/verify.js` | прогон движка в Node (тот же `core.js`) |
| `test/score.py` | честный CER по эталону |
| `models/eslav-ft.onnx` | второй чтец: наша CTC, дообученная на строках манги (3,9 МБ) |

Модели берутся из `models/` репозитория (`koma_det.onnx`, `koma_rec.onnx`,
`koma_dict.txt`) — те же файлы, что читает приложение.

## Замер (честный CER, ошибки / max(длина эталона, длина прочтения))

| страница | этот движок (браузер = Node) | Python-версия с бригадой чтецов |
|---|---|---|
| dense-a | 12,9 % · 4/9 дословно | 0,9 % · 7/9 |
| dense-b | 11,9 % · 4/9 | 3,3 % · 6/9 |
| dense-page | 12,7 % · 5/9 | 1,2 % · 7/9 |
| **среднее** | **11,0 %** · 13/27 | **1,8 %** · 20/27 · 26/27 |

(11,0 % — уже с двумя чтецами: страница грузит `models/eslav-ft.onnx`, дообученный
на нашем домене, и берёт его слово, только если у приложения слово не словарное, а у
эслава — словарное. Это «постфиксер только в плюс»: испортить он не может.
Один чтец приложения без него — 12,9 %.)

Почему разрыв: в браузер перенесён **один** чтец (тот, что в приложении). 1,8 %
даёт бригада из нескольких чтецов с голосованием и словарной починкой — в Python
её обучали на нашем домене. Порт бригады в браузер — следующая задача; сейчас
страница показывает то, что честно даёт перенесённая часть.

Проверено также, что браузерный движок **совпадает с Python-порт**ом: одинаковые
рамки (41 после дочистки), одинаковый текст строк, одинаковый порядок реплик.
Разница была только в моей чистке (греческие Δ/Β → Д/В) — исправлено в обеих версиях.

Время на страницу 720×1118: детектор ~0,5 с, чтение 41 строки ~3 с, всего ~3,6 с
(Chromium, WASM SIMD, 1 поток; потоки без COOP/COEP недоступны — и не нужны).

## Что осталось неверным (прямо)

- **Полоса интерфейса читалки.** На dense-b сверху висит «Справа налево» — подпись
  приложения. Отсекается правилом `uiBandTop` (верхние 10 % + светлый текст на
  тёмной плашке до края). Правило узкое: настоящие надписи на чёрных плашках манги
  ниже 10 % высоты не задеваются, но это эвристика, а не понимание.
- **Обрывки в конце реплик.** «ОТЦЕПИЛАСЬ ОТ», «Я НА ВАС,», «ГОТОВО НЕ ЗНАЮ,
  ПОМОЖЕТ ЭТО но.» — детектор даёт строку уже обрезанной по чернилам, и хвост
  («ХАНЫ», «ДУХИ», «ЛИ ЭТО, НО…») в рамку не попадает.
- **Путаница букв:** «БЬИ» вместо «БЫ И», «ВСЕ СЩЕ» вместо «ВСЁ ЕЩЁ», «ЗТО» вместо
  «ЛИ ЭТО». Это ошибки выбранного чтеца, а не движка; в Python их правит бригада.
- **Многострочные надписи подряд** («ОТЦЕПИЛАСЬ / ОТ ХАНЫ») при узком зазоре
  (0,6 высоты) иногда разваливаются на две реплики. На трёх страницах сейчас не
  разваливается, но запас небольшой.

## Что проверено, но выключено

- Второй проход с растянутым контрастом и чтение с растяжкой 0,85× / 1,15×:
  дают другой набор ошибок, но в сумме хуже (34,1 → 34,9 %). Оставлены в коде как
  опции `twoPass` / `stretch`, по умолчанию выключены — включил бы тот, у кого
  другая бумага/шрифт.
- Порог уверенности чтеца 0,8 (как в Python): режет строки, которые нужны для
  склейки реплики. Понижен до 0,2, а мусор отсеивается на уровне готовой реплики
  (как в Python) — так пропало дробление облачков на обрывки.

## Проверка идеи «конвейер из нескольких моделей»

Прогнал честный замер: тот же движок, те же рамки, но к чтецу приложения добавлены
два других CTC-чтеца (111 классов), с голосованием по словам.

| вариант | среднее CER | дословно |
|---|---|---|
| **один чтец (как сейчас)** | **49,5 %** | 6/27 |
| + второй, голосование | 52,9 % | 6/27 |
| + второй и третий, голосование | 53,4 % | 4/27 |
| «лучший по словарю» из двух | 55,4 % | 4/27 |
| второй / третий чтец в одиночку | 86,1 % / 87,8 % | 0/27 |

Вывод: слабый чтец в голосовании тянет вниз — больше моделей ≠ лучше. А вот
этап «постфиксер» (словарная починка слов) действительно работает:
**15,2 → 12,9 %**. Он у нас уже включён.

## Чужие открытые модели: что скачал, что замерил, что выбросил

Скачивал настоящие веса с Hugging Face и гонял на тех же трёх страницах, тем же
движком. Критерий отбора — не «известное имя», а CER и время: если модель
добавляет секунды и не даёт точности, она не едет.

| модель | размер | CER (как чтец) | время на 3 страницы | вердикт |
|---|---|---|---|---|
| чтец приложения `koma_rec` | 7,9 МБ | 12,9 % | 12,0 с | база |
| **наша `eslav-ft`** | 3,9 МБ | — | +0,3 с | **взято: 11,0 %** |
| `cyrillic_PP-OCRv5_mobile_rec` | 7,7 МБ | 11,4 % | 19,5 с (+6,7 с) | отказ: медленно, с эславом не даёт ничего |
| `PP-OCRv6_tiny_rec_cyrillic` | 2,5 МБ | 14,3 % | 13,3 с | отказ: хуже базы (13,3 % даже в паре) |
| `PP-OCRv6_medium_rec_cyrillic` | 62,7 МБ | 11,4 % | 65 с (+53 с) | отказ: 21,6 с на страницу, прироста нет |
| `cyrillic_PP-OCRv3_mobile/server_rec` | 8,6 МБ | 87–90 % | 0,5 с | отказ: словарь не совпал с моделью (каша) |
| YOLOv8m-seg пузырей (`kitsumed`) | **104 МБ** | — | **4,4–6,7 с на кадр** | отказ: одна сегментация дольше всей страницы |

Размер итоговой сборки: **37,5 МБ** (один файл) — в пределах вашего лимита.
Время страницы: **~4 с** в Chromium, из них детектор 0,5 с и чтение двумя чтецами ~3,3 с.

Что это значит по сути: **точность сейчас упирается не в количество моделей, а в
качество одного чтеца на нашем шрифте.** Чужой PP-OCR знает кириллицу лучше нас на
печатном тексте, но на мелких смазанных кропах манги он читает не лучше, а стоит
втрое дороже. Наша дообученная `eslav-ft` — единственная, что дала и точность, и
скорость. Следующий настоящий шаг — не «ещё модели», а дообучение чтеца приложения
на строках манги (у нас для этого есть `scripts/16_finetune_ctc.py` и синтетика).

## Другие форматы: PyTorch, TFLite, safetensors, Paddle

Проверял не «есть ли модель», а **даёт ли она что-то на наших страницах**. Формат
сам по себе ничего не решает: в браузер всё равно поедет ONNX (torch → ONNX или
tflite → ONNX — лишний шаг, размер не уменьшается).

| модель | формат | размер | качество у нас | скорость | вердикт |
|---|---|---|---|---|---|
| `taiga75/trocr-russian-print-1933` | PyTorch (334 млн параметров) | **1,34 ГБ** | хорошее: «ПОЖАЛУЙСТА,», «ЭТО ПРОКЛЯТИЕ», «сними с ханы» | **40 с на строку → 27 мин на страницу** | **отказ**: размер и скорость |
| `bluolightning/manga-ocr-tflite` | TFLite (энкодер+декодер) | 121 МБ | — | — | **отказ: в словаре 5450 символов, кириллицы 0** — русский текст физически не выдаст |
| `JustANormalTinkerer/hayai-ocr-v2-tflite` | TFLite | — | — | — | **отказ: в токенизаторе 16 000 токенов, кириллицы 0** |
| EasyOCR `cyrillic_g2` | PyTorch | ~15 МБ (rec) | 79,1 % CER сам, как второй голос 49,3 % против 49,5 % | **43 мс на строку — самый быстрый** | **отказ**: быстрый, но неточный и в голосовании ничего не даёт |
| `PaddlePaddle/cyrillic_PP-OCRv5_mobile_rec` | safetensors / Paddle | 7,7 МБ | те же веса, что уже проверенный ONNX (11,4 %) | — | **отказ**: смена формата не меняет числа |
| PP-OCR v3/v5/v6 | ONNX | 2,5–62,7 МБ | 11,4–14,3 % | +0,3…+53 с | см. таблицу выше — отвергнуты по замеру |

Ещё важное: **TFLite в браузере** требует отдельного рантайма (`tfjs-tflite`,
заброшен) — то есть это не «просто другой формат», а ещё один движок на 2–3 МБ
поверх onnxruntime. Для PyTorch путь тот же, что у нас был: экспорт в ONNX.

Повторить замеры можно так (веса не лежат в репозитории — они большие):

```bash
pip install easyocr            # PyTorch-чтец с русским, 43 мс на строку
pip install transformers sentencepiece torch   # TrOCR-russian, 1,34 ГБ
# TFLite: blender light — python -m pip install ai-edge-litert
```

**Итог по всем форматам один:** узкое место — не формат и не количество моделей, а
свой чтец на нашем шрифте. Побеждает то, что обучено на манге: наша `eslav-ft`
(+0,3 с, 12,9 → 11,0 %). Всё остальное либо медленнее в разы, либо не про русский.

## Сжатие весов: int8, fp16, «только кириллица»

Проверено на наших моделях, не на словах:

| приём | результат |
|---|---|
| int8 динамическое квантование (`quantize_dynamic`) | **в браузере не работает**: `Could not find an implementation for ConvInteger(10)` — у onnxruntime-web нет int8-ядер. `koma_rec` при этом ещё и не похудел (7,51 → 7,57 МБ) |
| fp16 (`onnxconverter_common.float16`) | чтецы: 7,51 → **3,82 МБ** и 3,76 → **1,93 МБ**, качество то же (11,0 %), скорость та же. Детектор fp16 **ломается**: 219 рамок вместо 41 |
| «оставить только кириллицу» в словаре | для TrOCR это срезает голову 50265×768 (~154 МБ), но **требует переобучения головы**, иначе мусор. До 10–100 МБ доводит только дистилляция |

Внедрено: оба чтеца в fp16, детектор в fp32. Сборка **37,5 → 30,2 МБ**, CER 11,0 %
без изменений. Скорость в WASM от fp16 не меняется: считать всё равно в float32.

## Дообучение чтеца на манге и манхве (01.11)

Разметил **113 настоящих строк** с четырёх страниц mangalib: `dense-a` (41, манга),
`kuro-p1` (31, манга, другой шрифт), `kuro-p2` (7, манга), `tyrant-p1` (29, манхва),
`reader-p1` (5, манхва). Модель училась на GitHub-раннере тремя этапами
**манга → второй шрифт → манхва**, проверка — целыми страницами, которых в обучении
не было (`kuro-p2`, `reader-p1`), чтобы строки одного облачка не утекали в обучение.

Что получилось на строках (CER, честно):

| страница | было | стало |
|---|---|---|
| dense-a (манга) | 2,9 % | **0,3 %** |
| kuro-p1 (манга, другой шрифт) | 19,5 % | **1,0 %** |
| kuro-p2 (манга, отложена) | 23,2 % | **6,0 %** |
| reader-p1 (манхва, отложена) | 2,5 % | 4,2 % |
| tyrant-p1 (манхва, в обучении) | 88,0 % | **34,3 %** |
| **всего** | **30,5 %** | **9,8 %** |

И честная оговорка: **на страницах (репликах) это почти не видно** — 11,0 % на демо-страницах
и 51 % на плотной kuro-p1 при любом чтеце, включая старый. Причина — не чтение строк,
а **склейка строк в реплики и отбраковка мусора**: все четыре комбинации чтецов дают
на kuro-p1 один и тот же CER 51 %. Поэтому в сборке оставлен прежний чтец (он лучший
по замеру — 20,4 % против 21,5 % по пяти страницам), а новые веса лежат в
`ownocr/model/eslav/eslav-ft-all.onnx` — они понадобятся сразу после починки склейки.

Мораль: **узкое место сейчас не модель, а сборка реплик.**

## Тесеракт как четвёртый чтец и разделение по жанрам (01.11)

Тесеракт 5.5 + `rus`, настройки подобраны замером: `--psm 13` и масштаб ×2
(7,4 % против 19,2 % у «дефолтного» psm 7). На 113 размеченных строках:

| чтец | манга (79) | манхва (34) | всего |
|---|---|---|---|
| приложение `koma_rec` | 28,8 % | **3,1 %** | 21,1 % |
| наш эслав (дообучен) | **1,1 %** | 29,8 % | 9,8 % |
| тесеракт | 8,0 % | 6,0 % | 7,4 % |
| эслав + тесеракт | 1,8 % | 13,3 % | **5,2 %** |
| приложение + тесеракт | 14,3 % | **2,8 %** | 10,8 % |

**У каждого жанра свой победитель:** манга — наш эслав (1,1 %), манхва — приложение
вместе с тесерактом (2,8 %). Политика «свой чтец на свой жанр» даёт **1,6 %** на всех
113 строках. По маньхуа и западным комиксам размеченных страниц нет — цифр не даю.

Тесеракт в браузер не идёт: 91 мс на строку на серверном C++ (у нас 23 мс и 3 мс),
а `tesseract.js` будет ещё в 5–10 раз медленнее. Он остаётся серверным точным режимом.

## Четвёртый жанр-чтец: вебтун и комиксы (01.11)

Размечено ещё 61 строка: маньхуа 28 («Нань Хао и Шан Фэнь», гл. 1–3) и комикс 33
(«Неуязвимый», гл. 1). Всего 174 строки на 12 страницах, четыре жанра.

| жанр | строк | приложение | эслав-манга | эслав-всё | **эслав-вебтун** | тесеракт |
|---|---|---|---|---|---|---|
| манга | 79 | 28,8 % | 11,2 % | **1,1 %** | 4,7 % | 8,0 % |
| манхва | 34 | 3,1 % | 75,4 % | 29,8 % | **0,2 %** | 6,0 % |
| маньхуа | 28 | 16,5 % | 11,0 % | 16,7 % | **1,9 %** | 9,2 % |
| комикс | 33 | 32,4 % | 28,2 % | 26,7 % | 31,2 % | **18,0 %** |

Отдельный чтец на вебтун обучен на раннере (`ownocr-finetune-genres.yml`) и **попадает

1,0 % на 141 строке). Поэтому в сборке появился переключатель «манга / манхва·маньхуа»,
и вторая модель едет с файлом (+1,9 МБ). Сборка 32,6 МБ, манга по-прежнему 11,0 %.

## Звуки (SFX) вместо голосов и полосы вебтуна (01.11)

Каждая найденная строка делится на **реплику** (читается голосом) и **звук**
(виден в списке с 🔊, голосом НЕ читается — вместо него играется эффект).

* классификатор — два признака: словарь звукоподражаний + повторы слогов
  («ХА-ХА-ХА», «А-ХА-ХАХА-Х») и «афишность» (строка выше медианной в 1,75 раза,
  ≤ 3 слов, ни одного словарного);
* замер на 12 размеченных звуках: **recall 75 %, precision 100 %** — реплику
  звуком не назвал ни разу (это важнее: пропущенный звук прочитается голосом,
  а реплика, названная звуком, потеряется);
* шесть эффектов (гонг, удар, взрыв, свист, смех, шлепок) синтезированы
  `make_sounds.py` — 235 КБ, внутрь сборки как data-URI;
* кнопка «🔊 Читать вслух» читает только реплики, на звуках играет эффект.

Исправлена **детекция полос вебтуна**: страница 800×5161 сжималась целиком до
148×960 и давала 0 рамок. Теперь режем на плитки 1500 px с перекрытием 160 —
та же страница даёт 20 рамок и 11 реплик за 3,5 с.
